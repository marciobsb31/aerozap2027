# TASK

ID: AZ-020

Responsável: A1

Estado: IN_PROGRESS

Título: Identity: cadastro, login, refresh token rotacionado, papéis e recuperação de acesso

Prioridade: Alta

Fase / Onda: Fase 2 — Identidade, planos e franquia (marco M2)

## Objetivo
Dar ao produto a sua primeira noção de pessoa: cadastro, autenticação, sessão e papéis.

## Contexto
RF-001 a RF-004, RF-007, RF-008, RF-099; DTC §2.4, §11.2, §13. O gateway (AZ-015) já valida JWT
HS256 com segredo compartilhado; este serviço passa a ser o emissor, e a ADR-0003 prevê a troca
para JWKS sem mudança para quem consome.

**Decisão em aberto (RF-001):** o método de cadastro ainda é PROPOSTA (e-mail + senha). Trate-o como
configuração do serviço, não como valor fixo espalhado pelo código, para que a entrada de um
provedor externo depois não vire migração.

## Dependências
- AZ-014

## Módulos que pode alterar
`apps/identity` (novo), `libs/java/*` quando a mudança servir a todos os serviços. Mudança em outro
módulo exige nova TASK para o dono.

## Entregáveis
- Serviço `identity` sobre o esqueleto da AZ-014 (Flyway, Problem Details, correlação, Outbox)
- Cadastro com aceite versionado e registrado de Termos e Política (RF-099)
- Login com access token curto e refresh token **rotacionado**, com detecção de reuso
- Papéis administrativos separados dos planos (RF-008); MFA de admin pode ficar para o M6, mas o
  modelo de papéis não
- Recuperação de acesso com token de uso único e expiração curta
- Eventos de identidade no contrato (`libs/java/event-contracts`), via Outbox
- Testes aplicáveis, documentação e evidências (DELIVERY REPORT)

## Critérios de aceite
- [ ] Cadastro e login funcionam de ponta a ponta pelo gateway, com evidência reproduzível
- [ ] Refresh token é rotacionado a cada uso; **reutilizar um token já usado invalida a família
      inteira de sessões**, e há teste que prova isso
- [ ] Tentativas de login são limitadas por identificador e por origem (RF-002)
- [ ] `user_id` sai do token e nunca do corpo ou da query da requisição (RF-007)
- [ ] Nenhuma senha, token ou segredo aparece em log, em resposta de erro ou em rastro
- [ ] Aceite de termos gravado com versão e data (RF-099)
- [ ] Ambiente rodando e verificável, com comando documentado

## Restrições
Senha nunca em texto claro nem com hash rápido: use um algoritmo de derivação com custo
(Argon2id ou bcrypt), com os parâmetros documentados.
Não modificar contratos compartilhados sem aprovação do CTO.
Respeitar as regras inegociáveis de `AGENTS.md`.

## Validação
A7 valida; A0 aprova.

## Andamento (05/11/2026)

Entregue e com teste: serviço `apps/identity` sobre o esqueleto da AZ-014; cadastro com aceite
versionado de Termos e Política; login com resposta idêntica para conta inexistente e senha errada;
token de acesso HS256 que o gateway já valida; refresh rotacionado com detecção de reuso que
derruba a família; limite de tentativas por conta; papéis separados do plano.

**Falta para fechar a TASK:** a recuperação de acesso. O token de uso único e a tabela existem, mas
o fluxo depende de um canal de envio (e-mail transacional) que o projeto ainda não tem — entregar
"recuperação" sem canal seria entregar um endpoint que não recupera nada. A porta de envio entra
junto com os templates transacionais pt/es.

**Correção (05/11/2026).** O código foi criado como `apps/identity`, um sexto deployable, sem que
os critérios de separação da ADR-0002 estivessem atendidos. Foi dobrado para dentro do
`platform-core` como o módulo `identidade`, com schema próprio, antes de qualquer merge.

## Achados da primeira execução dos testes de integração (05/11/2026)

Corrigidos em `bugfix/AZ-020-sessao-e-tentativas`:

- **Reuso de refresh não derrubava a família:** a exceção desfazia a revogação junto com a transação.
- **Limite de tentativas não funcionava:** toda senha errada respondia 500 e a conta nunca era bloqueada.
- O teste da senha curta esperava 422; o catálogo de erros define 400.
